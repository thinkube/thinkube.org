= The AI loop
:page-type: concept

_Get a model, fine-tune it, build on it, serve it — the four stages, in two minutes._

Real work crosses stages. You pull a model to try it, fine-tune it once you
know it's close, build something that calls it, and serve that to someone
else. Thinkube is organised around those four stages, and each one ends with
something you can point at.

== Get a model

You pick a model from the catalogue in thinkube-control and it is mirrored
from Hugging Face into Thinkube Registry — stored once, versioned, and served
from Thinkube Storage from then on.

Before you download anything, the platform tells you what will fit: which
backends can run the model, which of your GPUs have room, and roughly how much
memory it needs. The catalogue carries what each model needs to run correctly
— parameters, quantisation, context length, stop tokens — so the serving side
is configured from that rather than guessed.

== Fine-tune

You work in Thinkube Notebooks. Python environments are built from
definitions: a `fine-tuning` environment with peft, trl, bitsandbytes and
Unsloth, with the CUDA and torch pins already set for this hardware, and an
`agent-dev` environment with LangChain, CrewAI and AG2. You can add packages
to either, or define your own.

Every run is tracked in Thinkube Experiments. When a fine-tune produces
something worth keeping, you register it against the run that made it, and it
joins the catalogue as a model you can serve.

== Build

You describe an application in `thinkube.yaml`: which containers, which ports,
which routes, which services it needs. About twenty lines. From that, the
platform builds the images, deploys them, gives the application an address
with a certificate, and puts a login in front of it.

Templates give you a starting point — a web app with a backend and a
frontend, a model behind a Gradio UI, an embedding server. What you build from
one is a git repository you own.

== Serve

The LLM Gateway loads a model onto a GPU node and exposes it as one
OpenAI-compatible endpoint. It supports vLLM, TensorRT-LLM, Ollama and
text-embeddings backends, and picks memory settings from what the catalogue
says the model needs.

When you're done with a model, you unload it and the memory comes back.
Non-core components can be scaled to zero the same way, so what's running on
your machine is what you're using.

== Where the seams are

The interesting problems are between stages: a fine-tune that needs to be
served, an application that needs a model that isn't loaded yet. The
xref:playbooks/index.adoc[playbooks] are complete runs that cross every stage
and report what they measured.
