= Keeping it running
:page-type: how-to

_Check what is healthy, restart what is not, and know what a reboot, a system update, a cluster rebuild and the wipe script do to the platform and to your data._

.TL;DR
Ask Claude: "is NATS healthy?". Claude calls `get_service_details` and answers with the latest health check of each of the service's addresses, the error of any that failed, and its pods. "restart NATS" calls `restart_service`, which restarts its pods in place. The rest of this page is what happens to the platform when the machines themselves change.

== Why this is one sentence

thinkube-control checks every enabled service that has a health address, on a schedule, and keeps a day of results. The same reading is on the dashboard as a badge on each service card, and on the service's page as a history. You do not need a monitoring stack to know what is down, and you do not need `kubectl` to restart it.

[cols="1,2",options="header"]
|===
| You say | Claude calls

| "what's running?"
| `list_services_minimal`: every service, its type and whether it is enabled.

| "is Qdrant healthy?"
| `get_service_details`: the latest health check per address, pods, restarts, resources.

| "restart Qdrant"
| `restart_service`: a rolling restart of the service's pods.

| "turn off Langflow"
| `toggle_service`: scales an optional component to zero, and back. Core services cannot be turned off.

| "how are the GPUs?"
| `get_llm_gpu_status`: slots and memory per GPU node.
|===

== What starts again after a reboot

Every host-side piece the platform needs is a systemd unit enabled at boot. Nothing has to be started by hand.

[cols="1,2",options="header"]
|===
| Unit | Why it matters

| `thinkube-node-ip-sync`
| Runs before kubelet and writes the machine's current address into it, so the node does not come back with a stale one.

| `systemd-networkd`
| Creates `k8s0`, the fixed address of the Kubernetes API.

| `containerd`, `kubelet`
| The container runtime and the node agent; the cluster's pods come back from them.

| `k8s-api-proxy.socket`, workers
| Forwards the fixed API address to the control plane.

| `nvidia-host-driver-validation`, GPU nodes
| Tells the GPU Operator the host driver is ready, so GPU pods can start.

| `dns-config-verify`
| Restarts name resolution once the network is up, so your domain resolves through the cluster.

| `tailscaled`
| Puts the machine back on the tailnet.

| `cron`
| Runs the certificate renewal.
|===

== System updates

The installer holds four packages at the versions the cluster was installed with:

----
containerd.io  kubeadm  kubectl  kubelet
----

`apt upgrade` leaves them alone. Everything else moves with Ubuntu, including three that matter:

[cols="1,2",options="header"]
|===
| Package | What to know

| The NVIDIA driver
| Not held. A new driver takes effect after a reboot. The GPU Operator does not manage it; the platform uses whatever driver the host has, and the installer requires 580 or newer.

| The kernel
| Not held. The driver must build for a new kernel; check `nvidia-smi` after the reboot.

| Tailscale
| Not held. It updates from its own repository.
|===

Thinkube does not configure unattended upgrades; Ubuntu's own settings decide what installs on its own. To keep the driver where it is, hold it as the installer holds kubelet:

----
sudo apt-mark hold nvidia-driver-595-open
----

Use the package name `apt list --installed | grep nvidia-driver` shows on that machine.

== What survives what

[cols="2,1,1,1",options="header"]
|===
| | Pod restart | Cluster rebuild | `thinkube-wipe.sh`

| Your files on the shared filesystem
| kept
| data kept on disk, index removed
| removed

| Data in Thinkube Storage
| kept
| kept
| removed

| Thinkube Git, Registry, Identity, PostgreSQL
| kept
| removed
| removed

| Ubuntu, your account, sshd, the NVIDIA driver
| kept
| kept
| kept
|===

A cluster rebuild is the Kubernetes rollback playbook followed by a fresh install. The shared filesystem keeps its file contents in Thinkube Storage, which a rebuild does not touch, but its index of names and folders lives in PostgreSQL, which a rebuild deletes. Copy out what you need before you rebuild.

xref:kubernetes/what-the-install-changes.adoc[What the install changes on your machines] lists what the wipe script removes and what it leaves.

== Backups

The platform backs up one thing: the certificate and its key, encrypted with your sudo password and pushed to a private repository `thinkube-certificates` in your GitHub organisation, so a reinstall does not have to ask Let's Encrypt again. Nothing else is backed up. Your application repositories are safe when they are pushed somewhere outside the cluster; the rest, databases, registry, experiments, is on the machines.

== Upgrading Thinkube

There is no upgrade path between Thinkube versions. Thinkube is alpha software, and a future version may require installing from scratch. Each platform component has its own deploy and rollback playbooks, so one component can be deployed again without touching the others.

== Changing a token

[cols="1,2",options="header"]
|===
| Token | How

| GitHub
| xref:install:github-token.adoc[Connect to GitHub] has the steps: change `GITHUB_TOKEN` in `~/.env` on the control plane, deploy thinkube-control again, and revoke the old token.

| Hugging Face, Cloudflare, Tailscale
| No procedure is documented. The Cloudflare token the certificate playbook uses and the Tailscale key used when adding a node are read from the installer's inventory, not from `~/.env`.
|===

== When a name does not resolve

The install runs a small DNS probe on every node that logs one line for every lookup that fails and an hourly summary. Read it from Thinkube IDE:

----
kubectl logs -n kube-system -l app.kubernetes.io/name=dns-probe --prefix
----

With the optional Prometheus component installed, the same lookups and Cilium's own counters are collected as metrics, per node, so a failure has a before and an after. xref:kubernetes/networking.adoc[Networking and names] explains the path a lookup takes.

== Limits

* The health check reports a service as healthy when its primary address answers; read the per-address results for the others.
* No backup of databases, registry or files.
* No upgrade between Thinkube versions.
* The GPU memory the platform budgets comes from the driver the host has; a driver change is not validated by the platform.
