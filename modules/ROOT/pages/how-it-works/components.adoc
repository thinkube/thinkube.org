= Platform components
:page-type: concept

_Why there is a core set and an optional set, and what the toggle means._

Sixteen components are always present. Twenty more are in the catalogue,
installed from thinkube-control when you want them. The line between the two
is not taste — it is dependency.

== Core is the substrate

Every optional component's requirements resolve into the core. Six need
Thinkube Identity, five need PostgreSQL, five need Thinkube Registry. That
substrate is what makes installing an optional component a single toggle
rather than an afternoon of provisioning three datastores and registering an
OIDC client. It is already running, already wired, already logged in.

== Optional is yours

The catalogue has four categories — ai, data, infrastructure, monitoring —
and each entry declares what it needs and carries three playbooks: install,
test, uninstall. Every optional component can be removed the same way it
arrived.

Where the platform has no business having an opinion, it offers a choice and
makes none. Three vector stores. Four inference backends. Those are your
architecture. xref:why/index.adoc[Why Thinkube]
is the reasoning.

== Nothing has to stay resident

Every optional component has a toggle that scales it to zero. The LLM Gateway
unloads models. What is running on your machine is what you are using.

On a DGX Spark, where GPU memory is host RAM, that is not housekeeping —
every running component is AI capacity spent. Twenty components on a 128 GB
machine would be absurd if they all had to run. They don't.

== The catalogue is data

The lists live in `thinkube-metadata` — `optional_components.json`,
`models.json`, `mirror_images.json` — as a repository of their own.
thinkube-control reads them. Adding a model or a component is a data change
that ships independently of the platform.

xref:reference/components.adoc[The components catalog] lists every entry.
