= Architecture
:page-type: concept

_One base and three areas on it, and the lines between the areas that make them one platform._

.TL;DR
Under everything is unmodified Kubernetes on your machines, with the services every area needs: one sign-on, one filesystem, one registry, one database, the GPUs, and thinkube-control, the control plane you drive from Claude Code. On that base sit three areas: Thinkube GitOps, where apps are built and deployed from a push; Thinkube Models, where models are served, notebooks run and experiments are tracked; and Thinkube Tandem, where a sentence becomes a reviewed change. They are not separate products. A dataset a notebook writes is the file an app reads, the model a notebook fine-tunes is the endpoint the app calls, and the change Tandem delivers ships by the pipeline the app took.

== The decision

The base provides; the areas use. Nothing an area needs from another area is passed hand to hand: it goes through a service of the base that both areas already share.

Two things are deliberately not in the picture. Tandem's workers run on Claude Code, not on a model served in the Models area, so there is no line from Models to Tandem. And thinkube-control is a service of the base, not a fifth area: it is how every box is driven, and it appears once.

== What it saves you

Each line in the picture is one thing you never do by hand.

* *One filesystem.* Thinkube Storage is S3-compatible object storage, and JuiceFS puts a filesystem on it. A model you fetch lands there; a served model loads its weights from there; a notebook keeps its datasets and its experiment artifacts there; the workspace of Thinkube IDE is there. An app declares `storage` in its `thinkube.yaml` and mounts it. Nothing is copied from one area to another, because there is one place.
* *One registry.* The pipeline pushes your app images to Thinkube Registry. The same registry holds the mirrored model servers and the notebook images you build from definitions. One credential, one policy, one place to look.
* *One sign-on.* An app from the template, the notebooks, the dashboards and thinkube-control all register with Thinkube Identity. You sign in once. It is also why a Tandem reviewer can open your app in a browser at all: it signs in the same way you do.
* *One endpoint for models.* A model served in the Models area is one address behind the LLM Gateway, and an app built in GitOps calls it the way a notebook does. Change the model, and the app does not change.
* *One pipeline.* A push to Thinkube Git builds with Argo Workflows and deploys with ArgoCD. A template app takes that path; thinkube-control takes it; a Tandem delivery merges, pushes and takes it too, and Tandem's reviewers judge the result at the address the pipeline gave it.
* *One way to drive it.* Every box above is a sentence to Claude Code, answered by thinkube-control over MCP. xref:how-it-works/mcp-operation-model.adoc[The MCP operation model] is how.

=== The base, layer by layer

*Before the cluster.* The installer runs on an Ubuntu 24.04 machine, one of the servers or another, and deploys over SSH. Before Kubernetes exists it prepares each machine: grows the root volume Ubuntu leaves at 100 GB, sets up SSH between nodes, checks the NVIDIA driver, and on a DGX Spark applies the unified-memory tuning. It joins the machines to your Tailscale network. Then it moves the tokens you entered onto the control-plane host, so the machine you ran the installer from can be put away.

*The cluster.* kubeadm installs unmodified upstream Kubernetes. Cilium is the network and the load balancer. Routes are Gateway API. The cluster runs its own DNS, and certificates come from Let's Encrypt through your Cloudflare token. Every internal reference points at a stable virtual IP, and the one value tied to the physical network, the kubelet's node IP, is rewritten at boot from the default route. Move the machine to a different router and it comes back up. xref:how-it-works/kubernetes-underneath.adoc[Kubernetes underneath] is the detail.

*Storage and data.* Thinkube Storage, powered by SeaweedFS, with JuiceFS on top for the shared filesystem. PostgreSQL holds relational data for the platform and for your applications.

*Identity.* Thinkube Identity, powered by Keycloak. Every service registers as a client.

*The factory.* Thinkube Git holds your repositories, Argo Workflows builds images, Thinkube Registry stores them, ArgoCD deploys what the repository says, Thinkube Packages serves private Python packages, and Thinkube IDE is where you work, with Claude Code installed. xref:how-it-works/deploy-loop.adoc[The GitOps deploy loop] is how they connect.

*GPUs.* The NVIDIA GPU Operator with time-slicing; xref:how-it-works/gpu-multiarch.adoc[GPU and multi-arch] covers the budgeting between served models and notebooks.

*Control.* thinkube-control is the web UI and the MCP endpoint, one application. It reads the catalogues of models, optional components and images from `thinkube-metadata`, and it ships through the same deploy loop as your applications.

=== Core and optional components

Every optional component's requirements resolve into the base: six need Thinkube Identity, five need PostgreSQL, five need Thinkube Registry. That is what makes installing one a single sentence rather than an afternoon of provisioning three datastores and registering a client. The catalogue has four categories, ai, data, infrastructure and monitoring, and each entry declares what it needs and carries three playbooks: install, test, uninstall. Every optional component can be removed the same way it arrived, and every one has a toggle that scales it to zero; the LLM Gateway unloads models. On a DGX Spark, where GPU memory is host RAM, every running component is AI capacity spent, so what is running is what you are using.

Where the platform has no business having an opinion, it offers a choice and makes none: three vector stores, four inference backends. xref:why/index.adoc[Why Thinkube] is the reasoning; xref:reference/components.adoc[the components catalog] lists every entry. The lists live in `thinkube-metadata` as a repository of their own, so adding a model or a component is a data change that ships independently of the platform.

=== What survives what

[cols="2,1,1",options="header"]
|===
| | Pod restart | Cluster rebuild

| The shared filesystem | kept | data kept, index removed
| Data in Thinkube Storage | kept | kept
| Git, Registry, Identity and PostgreSQL volumes | kept | removed
| Ubuntu, your account, sshd, the NVIDIA driver | kept | kept
|===

A cluster rebuild is `19_rollback_control.yaml` followed by a fresh install: the data in Thinkube Storage stays, the platform's databases start over, and with PostgreSQL goes the shared filesystem's index of names and folders. xref:kubernetes/keeping-it-running.adoc[Keeping it running] says what that means for your files.

== Limits

* Tandem's workers run on Claude Code; a locally served model is not one of their options.
* An app reaches the shared data through the `storage` service it declares in `thinkube.yaml`; a container that declares none has no mount.
