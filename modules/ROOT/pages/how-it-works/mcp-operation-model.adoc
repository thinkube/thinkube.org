= The MCP operation model
:page-type: concept

_How thinkube-control's API becomes resources and tools for an assistant, and why the split matters._

.TL;DR
thinkube-control's API is one codebase exposed twice: to the browser, and to Claude Code through MCP at `/mcp`. Reading state is a resource Claude consults freely; changing state is a tool it uses only when you ask.

thinkube-control is a FastAPI application. Every endpoint carries an
`operation_id`, and the application is wrapped with `ExtendedFastApiMCP` and
mounted at `/mcp` alongside the web UI. One codebase serves both; there is no
separate MCP implementation to fall out of step.

The operations exposed over MCP are chosen deliberately, in an include list
annotated in the source. Each is classified as a resource or a tool.

== Resources

`GET` endpoints become resources — things the assistant may read as context
without being asked. Among them:

* `list_services_minimal`, `get_service_details`, `get_service_health_history`
* `describe_pod`, `get_container_logs`
* `get_cluster_resources`, `get_llm_gpu_status`
* `get_model_catalog`, `get_llm_load_options`, `get_deployment_status`

A resource answers a question. It changes nothing.

== Tools

Endpoints that change state become tools — used only when you ask. Among them:

* `deploy_template`, `redeploy_template`
* `submit_model_mirror`, `load_llm_model`, `unload_llm_model`
* `create_jupyter_venv`, `build_jupyter_venv`
* `toggle_service`, `restart_service`, `install_optional_component`
* `search_thinkube_docs`, `get_thinkube_doc`

A tool is an instruction. The assistant does not reach for one on its own.

== Why the split

Diagnosis before action. An assistant that can read a pod's logs and health
history can work out what is wrong before it touches anything, and can tell
you what it found. An assistant that could only act would have to guess.

And nothing mutates without a request. The line between "look" and "do" is
drawn in the API, not left to the assistant's judgement.

== The documentation

`search_thinkube_docs` and `get_thinkube_doc` read the documentation site
deployed inside the cluster. They are tools rather than resources: a search
takes a query, so the assistant calls it rather than having the result in
context. Until that deployment exists, the tool returns
`docs_not_deployed` with the instruction to deploy it. Once it does, the
assistant answers documentation questions from the pages themselves.
