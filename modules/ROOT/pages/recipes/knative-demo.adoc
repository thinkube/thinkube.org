= A service that scales to zero
:page-type: how-to

_Deploy the Knative demo template: a small HTTP service that runs no pods while nobody calls it, starts one on the first request, and adds more under load._

.TL;DR
Ask Claude: "make a service called knative-demo from the Knative demo template", then "call knative-demo and tell me how many pods it has". The service answers at `knative-demo.<your domain>` with a greeting and the name of the pod that served it. Between requests it has no pods at all; the first request starts one, and a burst of requests starts more, up to three.

== Why this is one sentence

Most of what you deploy is called now and then: a webhook, a small API, a tool for one person. Keeping a pod running for it holds memory for nothing, and on a DGX Spark memory is also GPU memory. A Knative service holds nothing while it is idle. The template is the smallest service that shows it, so you can see scale to zero work on your cluster before you build on it.

The optional component Knative must be installed. Ask Claude "install Knative" if *Knative Services* is not in thinkube-control.

== What you get

[cols="1,2",options="header"]
|===
| Address | Answers

| `https://knative-demo.<your domain>/`
| A greeting, the request number, the simulated work and the pod's name, as JSON.

| `/health`
| The pod's uptime and how many requests it served.

| `/scale-test`
| The same simulated work, for sending many requests at once.
|===

On the reference cluster, the first request after an idle period answered:

----
{
  "message": "Hello from Knative!",
  "app": "knative-demo",
  "simulated_work_ms": 100,
  "hostname": "knative-demo-00001-deployment-76d89b46db-nddf9",
  ...
}
----

Thirty requests sent at once started a second pod. Once the requests stopped, the service went back to no pods.

*Knative Services* in thinkube-control shows each service, its pods now, its limits and whether it is scaled to zero:

== By hand, and what is happening underneath

The descriptor is what makes it a Knative service rather than an always-on app:

[source,yaml]
----
spec:
  deployment:
    type: knative
    minScale: 0
    maxScale: 3
    containerConcurrency: 5
    timeoutSeconds: 30
  containers:
    - name: demo
      build: .
      port: 8080
      size: small
      health: /health
  routes:
    - path: /
      to: demo
----

`minScale: 0` lets it go to no pods. `containerConcurrency: 5` is how many requests one pod takes before Knative starts another, and `maxScale` caps the count. A request that arrives while there are no pods waits for one to start. xref:reference/thinkube-yaml.adoc[thinkube.yaml] lists the rules for a Knative service: one container, no GPU, no mounts, a timeout of at most 900 seconds, and of the platform services only `database`, `cache` and `queue`.

Two settings are environment variables in `thinkube.yaml`: `GREETING`, the message, and `SIMULATE_WORK_MS`, the work each request pretends to do. Change them in your copy of the repository and push; the push builds and deploys, like any app.

Everything else is the xref:how-it-works/deploy-loop.adoc[GitOps deploy loop]: your repository in Thinkube Git, the image in Thinkube Registry, ArgoCD deploying what the repository says. The name under your domain is mapped to the service, and requests reach it through the gateway the Knative component brings.

== Limits

* The service is not behind your login: any device on your tailnet can call it.
* The first request after an idle period waits for a pod to start.
* A Knative service has one container and no GPU; a model server is an app or a component, not a Knative service.
