= What a playbook is
:page-type: concept

_A playbook is one piece of work carried across every stage of the platform, written from a run that actually happened. Which one to read first, and what each needs._

The rest of the documentation is organised by stage: get a model, fine-tune, build, serve. That is the right shape when you know which step you need. It is the wrong shape when you want to know whether the whole thing works, because real work crosses every stage and the interesting part is the seam between them: the fine-tune that has to be served, the index that has to be built before the agents can argue, the application that needs a change the template did not make.

A playbook crosses those seams in one run. Each one on this site was run on the reference cluster, and the page reports what appeared at each step, including the steps that failed and what was done about them. Nothing on these pages is a result the author hoped for.

Two of the three ship as notebooks in Thinkube Notebooks, under `thinkube/notebooks/examples/` in the file browser, so the page you read and the code you run are the same thing. The third is a walkthrough of Thinkube Tandem on a deployed application.

== The three

== Which one first

* If you have not loaded a model yet, start with the xref:start-here/quickstart.adoc[Quickstart]; every playbook assumes the gateway answers.
* If you want to see the platform's services used together without training anything, read the research assistant. It is the one with no GPU training, and its first notebook doubles as a check that the services are reachable.
* If you want a model of your own at the end, read the fine-tune. It is the longest; the notebook has a demo scale that runs every stage on a smaller set.
* If you want to see what Tandem does with a sentence, read the nine sentences. It is the only one where nothing is typed in the language of software.

== What a playbook page promises

Every step is something you do and something you see afterwards. Where a number is quoted, it was measured on the run the page describes, on the hardware it names. Where a step failed on that run, the page says so and says how it was resolved. What a playbook does not carry is a time figure: the alpha runs on two hardware configurations and yours will be the third.
