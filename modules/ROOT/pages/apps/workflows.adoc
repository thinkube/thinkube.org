= Run a pipeline from your app
:page-type: how-to

_Give your application its own Argo Workflows access, and run multi-step pipelines in its own images._

.TL;DR
Ask Claude: "add workflows to the services of my app". Claude adds `workflows` under `services` in the app's `thinkube.yaml`, commits and pushes. The commit regenerates the app's manifests and the push deploys them. From then on the app's backend submits Argo workflows into its own namespace, running steps in its own images and passing files between steps through Thinkube Storage.

== Why this is one sentence

A pipeline needs more than a workflow engine: permission to create workflows, an identity for the steps, somewhere to keep the files the steps pass along, and the names of the images to run. Argo Workflows is already part of Thinkube. Declaring the service gives the app the rest, inside its own namespace, where its secrets, its image pull secret and its resource budget already are. The app writes the pipeline; the platform has set up everything it runs on.

== Declare the service

In `thinkube.yaml`:

[source,yaml]
----
services:
  - database
  - workflows
----

`workflows` takes no `:name` suffix: an application has one. Commit the change. The pre-commit hook regenerates `k8s/` and adds `k8s/workflows.yaml` to the commit. Push, and the deploy applies it.

A Knative service cannot declare it. The deploy stops with:

----
Service 'workflows': workflows is not allowed in Knative services. database, cache, and queue are allowed.
----

== What the app receives

In the app's namespace:

[cols="1,3"]
|===
| Resource | What it is for

| ServiceAccount `<app>-workflows`
| Every pod of the app runs as this account, so its token carries the permissions below.

| Role and RoleBinding `<app>-workflows`
| Create, read, update and delete workflows, workflow templates and cron workflows; report step results; read pods and their logs. In this namespace only.

| ConfigMap `artifact-repositories`
| The namespace's default artifact repository: bucket `argo-artifacts` in Thinkube Storage, under the prefix `<app>/`.

| Secret `argo-artifacts-s3`
| The storage credentials that repository uses.
|===

In every container:

[cols="1,3"]
|===
| Variable | Value

| `WORKFLOWS_NAMESPACE` | The app's namespace.
| `WORKFLOWS_SERVER_URL` | `http://argo-workflows-server.argo.svc.cluster.local:2746`
| `WORKFLOWS_SERVICE_ACCOUNT` | `<app>-workflows`
| `WORKFLOWS_UI_URL` | `https://argo.<your domain>/workflows/<namespace>`
| `CONTAINER_IMAGE_<NAME>` | One per container in `thinkube.yaml`, such as `CONTAINER_IMAGE_BACKEND`: the image that container's deployment runs, `registry.<your domain>/thinkube/<app>-<container>:<build tag>`. The value follows the deployed build, so a step runs the same code as the app that submitted it, and a rollback of the app rolls back its steps.
|===

== Submit a pipeline

The client is hera, which the web app template's backend image already contains. This two-step pipeline writes a file in step one and reads it in step two, both steps in the backend's own image:

[source,python]
----
"""Submit a two-step pipeline from inside the application.

Everything it needs is already in the environment: the namespace to submit
into, the Argo server to submit to, and the application's own image to run
the steps in. The pod's projected token is what authorises the submission.
"""

import os
from pathlib import Path

from hera.workflows import Artifact, Container, Steps, Workflow, WorkflowsService

TOKEN = Path("/var/run/secrets/kubernetes.io/serviceaccount/token").read_text()

namespace = os.environ["WORKFLOWS_NAMESPACE"]
image = os.environ["CONTAINER_IMAGE_BACKEND"]

workflows = WorkflowsService(
    host=os.environ["WORKFLOWS_SERVER_URL"],
    verify_ssl=False,
    token=TOKEN,
    namespace=namespace,
)

with Workflow(
    generate_name="wf-check-pipeline-",
    entrypoint="pipeline",
    namespace=namespace,
    service_account_name=os.environ["WORKFLOWS_SERVICE_ACCOUNT"],
    image_pull_secrets=["app-pull-secret"],
    workflows_service=workflows,
) as w:
    produce = Container(
        name="produce",
        image=image,
        command=["sh", "-c"],
        args=[
            "mkdir -p /tmp/out && "
            "echo \"written by step one at $(date -u +%H:%M:%SZ)\" > /tmp/out/message.txt && "
            "cat /tmp/out/message.txt"
        ],
        outputs=[Artifact(name="message", path="/tmp/out/message.txt")],
    )
    consume = Container(
        name="consume",
        image=image,
        command=["sh", "-c"],
        args=["echo 'step two read:' && cat /tmp/in/message.txt"],
        inputs=[Artifact(name="message", path="/tmp/in/message.txt")],
    )

    with Steps(name="pipeline"):
        produce(name="step-one")
        consume(
            name="step-two",
            arguments=[
                Artifact(
                    name="message",
                    from_="{{steps.step-one.outputs.artifacts.message}}",
                )
            ],
        )

created = w.create()
print(created.metadata.name)
----

The workflow names no artifact repository: the namespace's default is used. `image_pull_secrets` lets the steps pull the app's own images.

On the reference cluster, run from the backend pod of the verification app `wf-check`, both steps succeeded in `registry.thinkube.com/thinkube/wf-check-backend:latest`, and step two printed what step one wrote:

----
step two read:
written by step one at 09:28:12Z
----

The file travelled through Thinkube Storage under the app's prefix:

----
wf-check/wf-check-pipeline-lk4hc/wf-check-pipeline-lk4hc-produce-56862374/message.tgz
----

== Give a step the app's secrets

The secrets an app declares in its `manifest.yaml` reach the app's own containers. A step does not receive them unless it asks for them: add `env_from` with the Secret `<app>-secrets` to the step. In the script above, a step that reads a secret is defined like this:

[source,python]
----
from hera.workflows import Container, SecretEnvFrom

read_token = Container(
    name="read-token",
    image=os.environ["CONTAINER_IMAGE_BACKEND"],
    command=["sh", "-c"],
    args=['echo "SECRETS_CHECK_TOKEN has ${#SECRETS_CHECK_TOKEN} characters"'],
    env_from=[SecretEnvFrom(name=f"{namespace}-secrets")],
)
----

The namespace and the app have the same name, so `+f"{namespace}-secrets"+` is the app's Secret. The step receives every secret the app declares and the store holds.

On the reference cluster, with `wf-check` declaring `SECRETS_CHECK_TOKEN`, the step printed:

----
SECRETS_CHECK_TOKEN has 33 characters
----

The same step without `env_from` printed:

----
SECRETS_CHECK_TOKEN has 0 characters
----

== Watch it

Open the address in `WORKFLOWS_UI_URL`: the Argo UI for the app's namespace, with each run, its steps, their logs and their artifacts. From a terminal:

----
kubectl get workflows -n <app>
----

== What the app may do

Checked with `kubectl auth can-i` as `wf-check-workflows`:

[cols="2,1,1"]
|===
| Action | In `wf-check` | In `argo`

| Create, list and delete workflows | yes | no
|===

It cannot list workflows in `thinkube-control`, read Secrets in its own namespace, or list the cluster's nodes. Nothing the app submits can touch the platform's own image builds, which run in `argo`.

== Limits

* Knative services cannot declare `workflows`.
* One `workflows` service per application.
* The control panel does not list an app's runs; use the Argo UI or `kubectl`.
* Step pods run in the app's namespace, under its LimitRange and ResourceQuota.
* The storage credentials in `argo-artifacts-s3` are the platform's: the `<app>/` prefix names the app's files but does not keep other apps out of them.
* hera must be in the image the pipeline is submitted from.
