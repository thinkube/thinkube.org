= Gap analysis
:page-type: reference

_What the documentation does not yet say, and what each gap is waiting for._

Every page on the site is written and was checked against the source of the thing it describes. The gaps below are the ones that remain, each with the fact or the act that closes it. This page is updated when one closes.

== Facts only the maintainer can supply

[cols="2,3",options="header"]
|===
| Gap | What closes it

| Whether an existing Python virtual environment, an Ollama install and its models survive the installer in practice
| A statement from a machine where they were present before the install. The playbooks do not remove them and do not mention them; xref:install:overview.adoc[Install Thinkube] says only what they create.

| What happens to a node six months on: `apt upgrade`, a kernel update, an NVIDIA driver update, and how a newer Thinkube is applied to a running cluster
| The maintainer's account of an upgrade that was done, or the statement that none has been done yet. The alpha block already says a future version may require a reinstall.

| Captures of the desktop installer's screens
| The installer runs on a laptop, not in the cluster, so xref:contributing/screenshots.adoc[the capture tool] cannot take them. One capture per screen listed on xref:install:overview.adoc[Install Thinkube].
|===

== Known mismatches between pages and product

These are documented as the product is, and listed here so a reader who finds them knows they are known.

* The Thinkube Notebooks theme still shows the service's former name, the one that ends in "Lab", in its header and in the *Server Options* form. The service registers as Thinkube Notebooks and the pages use that name.
* The installer's completion screen labels Thinkube IDE "Code Server" and prints `code.<your domain>`; the service registers at `ide.<your domain>`, which is the address the pages give.
* thinkube-control's `install_optional_component` failed within two seconds for `vllm` and `text-embeddings` on the reference cluster, with no reason in the logs; deploying the same templates with `deploy_template` succeeded. The pages describe the path that worked.
* Thinkube Tandem's MCP tools `read_space` and `read_run` report an empty space and no run for a space that the IDE shows populated and running; the pages describe what the IDE shows.
* In the walkthrough run recorded on xref:playbooks/nine-sentences.adoc[Nine sentences], Thinkube Tandem's live phase reported *the platform never finished building it* while the application was already built and answering at its address; *Ask the platform again* settled it. The four units that judge the running product were never reached, and the page says so.
* thinkube-control's `build_jupyter_venv` for `agent-dev` failed on the reference cluster after fifteen seconds, at the playbook task *Get all cluster nodes*, with *Separator is found, but chunk is longer than limit*; nothing was rebuilt. The venv on disk dates from before its template and carries `ag2` 1.0.2, which has no `autogen` module, where the template pins `ag2[openai]==0.10.2`. The pinned version was installed into the venv by hand on the node running the notebook server so that `03-multi-agent.ipynb` could import it.
* `jupyter_execute_all_cells` executes through the notebook's collaborative document, so it needs the notebook open in a JupyterLab tab. When the tab closes mid-run, the remaining cells do not run and the outputs of the cell in flight are not saved.
* Loading a second model on the vLLM backend replaced the first: after `Qwen/Qwen3-8B` was loaded on `vllm-tkspark`, the backend listed only that model, while the registry still showed `Qwen/Qwen3.5-4B` as *available* on the same backend. The gateway's `/v1/models` returned an empty list throughout.
* The three asynchronous notebook endpoints exist on thinkube-control's REST API and not as MCP tools; xref:control:notebooks.adoc[Notebook execution over MCP] says so.
