= Fine-tune a model
:page-type: concept

_What fine-tuning looks like on Thinkube, and what to reach for._

You fine-tune in Thinkube Notebooks, in an environment that is already built
for your hardware, and the run is tracked in Thinkube Experiments. When the
result is worth keeping, you register it, and it becomes a model you can
serve.

== The environment

The `fine-tuning` environment carries peft, trl, bitsandbytes and Unsloth,
with the CUDA and torch versions pinned to what this hardware needs. It is
built from a definition, per architecture, so it can be rebuilt rather than
remembered. You can add packages to it or define your own from it.

== Tracking

Every run logs to Thinkube Experiments — parameters, metrics, artifacts.
Registering a model against its run is what turns a checkpoint on disk into
an entry in the catalogue, with the run that produced it one click away. From
there the LLM Gateway can load it.

image::experiments-home.png[Thinkube Experiments, the experiments list]

== Two halves of Thinkube Experiments

Tracking holds experiments and runs: what you tried and what happened,
identified by a run id. The model registry holds named, versioned models:
what is deployable, identified by name and version. A model registered with
its `run_id` links the two, so a version can be walked back to the reward
curve and the parameters that produced it. A version registered without that
link is a set of weights nobody can account for.

Registering makes a model exist; the catalogue makes it loadable. A
fine-tune also needs an entry in `models.json` in `thinkube-metadata` with
`is_finetuned: true` and the backend that serves it, or `load_model` answers
"not found" however healthy the registry entry looks.

== One GPU or several

The environment carries Unsloth, and TRL with PEFT and accelerate. The
example notebook trains with Unsloth on one GPU. TRL's trainers run across
several GPUs with accelerate; if you have more than one card and want them
all in one run, that is the path.

== A complete run

xref:playbooks/zebra-grpo.adoc[Fine-tune on verifiable rewards] is the whole
loop: mirror a base model, train with GRPO against a program that grades each
attempt, evaluate before and after, register, serve, call. The notebook and
the page are the same thing.
