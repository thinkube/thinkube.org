= Models
:page-type: concept

_Get a model, serve it, put it behind your app, measure it, improve it: all open, all from one place. What that rests on, what it saves you, and where each part is explained._

.TL;DR
Ask Claude: "get Qwen/Qwen3-8B and load it on the spark". The model is mirrored once into your registry and served at `llm.<your domain>` through the OpenAI or Anthropic API. Write your app against that address. When the prompt is not enough, fine-tune the model in a notebook, register the result, and load it at the same address.

== The decision

A model you own and can change beats a model you rent and cannot. So Thinkube serves open models only, keeps them in your own registry, and gives every one of them the same address and API through the LLM Gateway. The catalogue carries what each model needs to run, so the platform can say what fits your GPU before you download anything and configure the server from the entry rather than from a guess. xref:why/index.adoc[Why Thinkube] makes the case; xref:concepts/models.adoc[Concepts: models] explains the words.

== What it saves you

* *One download, ever.* A model is mirrored once from Hugging Face into Thinkube Registry and served from your storage from then on.
* *One address, every model.* Your code speaks to `llm.<your domain>`; the model behind it changes without the code changing.
* *No sizing by hand.* The platform computes what fits from the catalogue and your GPU budget, and refuses a load that will not fit.
* *No bill per experiment.* Once the hardware is yours, trying a model, comparing two, or fine-tuning costs nothing extra.

== Where it shows up

[cols="1,2,2",options="header"]
|===
| Page | You do | You end with

| xref:lifecycle/get-models.adoc[Get a model]
| Ask what fits, mirror it.
| The weights in your registry, the model marked ready to load.

| xref:lifecycle/serve.adoc[Serve a model]
| Load it on a GPU node, call it, unload it.
| A model answering at `llm.<your domain>`.

| xref:lifecycle/notebooks.adoc[Thinkube Notebooks]
| Start a server, pick an environment, call a served model from Python.
| A notebook with `tk_llm` configured for your gateway.

| xref:lifecycle/fine-tune.adoc[Fine-tune]
| Train in a notebook, track the run, register the result.
| A model of your own in the same catalogue, served the same way.
|===

The seam between them is what the platform carries for you: a fine-tuned model is served exactly like a mirrored one, and the app that calls the gateway never knows which it got.

== Limits

* Every served model needs a catalogue entry; a model that is not in the catalogue needs one added first.
* A vLLM backend serves one model per node at a time.
