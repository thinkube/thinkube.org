= Serve a model
:page-type: how-to

_Load a mirrored model onto a GPU, call it, and unload it when you're done._

.TL;DR
Ask Claude: "load Qwen/Qwen3.5-4B on the spark". It answers `loading` with the backend it chose, then `available`, and from then on the model answers at `llm.<your domain>` behind your login, through the OpenAI or Anthropic API your code already speaks. "unload it" gives the GPU back.

== Why this is one sentence

Serving is a system, not a command: a process holding the weights, batching requests through the GPU, an address with a certificate, a login, a token, and one API for every model. The LLM Gateway is that system, built once, so loading a model is the only step left for you, and the application you write against the gateway does not change when the model does.

In thinkube-control this is *LLM Gateway*. The inference engines are optional
components; install vLLM, TensorRT-LLM, Ollama or text-embeddings from
*Optional Components* first, and the gateway discovers them.

image::cp-llm-serve.png[The LLM Gateway page of thinkube-control with two models loaded: a chat model on the DGX Spark through vLLM, an embedding model on the RTX 3090 node through text-embeddings]

== Load it

----
› load Qwen/Qwen3.5-4B on the spark with a 32k context
----

The LLM Gateway picks a backend and, unless you name one, a node, and loads
the model. It answers `loading` with the backend it chose, then `available`.
On the reference cluster, `Qwen/Qwen3.5-4B` loaded through `vllm-tkspark`;
the page then showed the model holding one of the Spark's four slots with an
estimated 34.9 GB of its unified memory, and the backend healthy.

== Choose how it loads

Loading takes options. Say them in words, or set them in thinkube-control:

* *tier* — `flexible` loads through Ollama when the model supports it:
  quantised, quick to load, less memory. `performance` loads through vLLM or
  TensorRT-LLM: full precision, higher throughput.
* *backend* — name one: `vllm`, `tensorrt-llm`, `ollama`, `text-embeddings`.
* *node* — which GPU node. The gateway chooses if you don't.
* *max_context_length* — cap the context to save memory.
* *keep_alive* — Ollama only: how long the model stays loaded after the last
  request.
* *num_speculative_tokens* — for models with a speculative-decoding
  configuration, the draft depth.

----
› load Qwen/Qwen3.5-4B on tkamd2 with a 16k context
----

== See what's loaded

----
› what's on the GPUs?
----

Claude reads the GPU status: each node's slots, what holds them, memory used.
On a DGX Spark it also shows the AI budget and the reserve.

== Call it

Every loaded model sits behind one endpoint at `llm.<your domain>`, which
speaks both the OpenAI API and the Anthropic Messages API. From a notebook:

[source,python]
----
from tk_llm import get_openai_client

client = get_openai_client()
response = client.chat.completions.create(
    model="Qwen/Qwen3.5-4B",
    messages=[{"role": "user", "content": "Hello"}],
)
----

From anywhere else, any OpenAI client pointed at the gateway with a token
from thinkube-control under *API Tokens*, sent as a bearer token or as
`x-api-key`. The same call from a shell on the reference cluster, with
"Say hello in one word." and thinking switched off, came back with
`Hello!` and a usage of 18 prompt tokens and 3 completion tokens.

Qwen3.5 is a reasoning model: it thinks before it answers, and the thinking
is charged against `max_tokens`. With a small budget the visible answer is
empty; the notebooks that call it either pass
`extra_body={"chat_template_kwargs": {"enable_thinking": False}}` or leave
room with `max_tokens=1024`. With a 20-token budget and thinking on, the
first example notebook got no content back at all.

== Unload it

----
› unload Qwen/Qwen3.5-4B
----

The slot and the memory come back. Loading it again is fast: the weights are
already in Thinkube Storage.

== Limits

* A vLLM backend serves one model per node; loading another on the same node replaces it.
* A reasoning model spends `max_tokens` on thinking first; give it room or switch thinking off, as the call below shows.
* Tool calling needs a model the catalogue marks for it, served with a parser that matches the model's call format.
